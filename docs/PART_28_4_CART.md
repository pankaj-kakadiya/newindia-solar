# Part 28.4 — Purchase and cart hand-off

## Branch recovery note

Before this part could start, `main` and `work/step28` had diverged: `main` had merged the Step 29 ACDB/DCDB manufacturing cost engine (admin components/enclosures, checkout support for custom configurations, Razorpay payment) without ever merging Step 28 (28.1–28.3: gallery, variants, price/quantity). `work/step28` had none of that Step 29 code. Both branches had independently edited `app/cart/page.tsx`, `app/product/[slug]/page.tsx`, `app/bulk-order/page.tsx` and `components/CartProvider.tsx`.

Per owner direction, `work/step28` was merged in rather than discarded or redone. The four conflicts were resolved by keeping the newer, tested Step 28 implementation as the base (decimal-safe `linePrice`/`cartAmounts`, `addChecked`, `ready`/`storageWarning`, the V2 `ProductDetail` page) and re-adding what only `main`'s line had: the product-thumbnail cart row (`CartMedia`), the ACDB/DCDB combo builder's session-storage RFQ hand-off (`nis-builder-rfq-*`), and the `BuyerCartItem` fields custom builds need (`customType`, `templateId`, `selectedValueIds`, `visualSelections`, `visualPreview`). No database writes, prices, master records, brand assets, DNS or hosting settings changed as part of this merge; `app/checkout/page.tsx` was untouched by `work/step28` and required no merge.

## Implemented

- **Repeated additions**: `mergeCart` already merged same-SKU lines; `readCart`/`mergeCart` now reject a saved or added line whose optional numeric fields (`gstRate`, `minQty`, `quantityStep`) are the wrong type or out of range, and reject an incomplete `custom` line (missing `templateId` or any selection) outright rather than letting it reach checkout and fail there unexplained. A malformed line is dropped, never silently coerced.
- **Aggregate cart limit**: `mergeCart` now refuses a **new** distinct line once the cart holds `MAX_CART_LINES` (500) lines, while still allowing quantity to merge into an existing line at that cap.
- **Concurrent additions**: `CartProvider.addChecked`/`addAllChecked` re-read the persisted cart from `localStorage` immediately before merging (`latest()`), not only from the in-memory ref updated by the `storage` event. This narrows the window in which two near-simultaneous additions (two tabs, or two "add to cart" actions in quick succession) could otherwise lose one of them or oversell stock. A new `mergeCartMany`/`addAllChecked` applies a batch of additions atomically, so a combo purchase (ACDB + DCDB together) cannot be left with only one side in the cart if the other fails a fresh stock check.
- **Price/tax consistency across every standard "add to cart" path**, not only the product detail page: the catalogue quick-add (`ShopCatalogue`) and the ACDB+DCDB combo builder (`ComboBuilder`) now save `gstRate` (and the catalogue quick-add saves `minQty`) with the line, so the cart page's per-line tax and the order summary match what `/checkout` will show, instead of falling back to "tax needs refresh." Both now go through `addChecked`/`addAllChecked` with an explicit stock ceiling instead of the unchecked legacy `add()`.
- **Reorder from a past order** (`account/orders/[id]`) now adds each returned item individually through `addChecked` and reports per-item failures next to the server's own `notAdded` list, instead of throwing on the first failing item and silently dropping the rest of the reorder. The reorder API (`/api/buyer/orders/[id]`) now also returns the live `gst_rate` and quantity step for standard lines, for the same tax-consistency reason.
- **Buy Now**: unchanged in behavior (already implemented in the V2 `ProductDetail` component carried over from `work/step28`) — adds the checked selection, then opens `/checkout` with the existing cart; it does not place an order or take payment. Verified end-to-end against a synthetic fixture.

- **298 pure regression tests passed** (existing gallery/variant/catalogue suite) plus the pre-existing **41-scenario PGlite checkout-integrity suite** (server-side price/GST/stock authority, duplicate-line and cross-cart stock races, retry idempotency, RLS) — all unaffected by this change.

- **4 new browser tests** (`tests/cart-part284.browser.cjs`) against an intercepted synthetic fixture with production writes blocked: repeated Add to Cart clicks merge into one persisted line; Buy Now adds the item and opens `/checkout` without placing an order; a corrupted saved cart line is dropped without breaking the cart page, across a reload; and two tabs sharing one cart converge on the true remaining stock (the second tab's own stock display and quantity limit react to the first tab's write, and the combined total never exceeds stock).
- The full existing browser suite was re-run (65 specs): all product-detail, variant, gallery and the new cart specs passed. Two `gallery-part282` cases that load real external catalogue image URLs, and one pre-existing `builder-buyer` (ACDB/DCDB drag-and-drop) case, failed in this sandbox for reasons unrelated to this change (this sandbox's network path to the live asset host, and an unrelated flake in the Step 29 builder drag interaction); neither file was touched by this part.
- Full Next.js production build and a strict standalone TypeScript check both passed.
